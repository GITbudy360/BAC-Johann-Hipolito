\section{Experimental Test Flow}
\label{sec:test-flow}

The evaluation exercises a deterministic, five-phase procedure known as the "Data-Safety Experiment." This procedure tests a single, highly controlled scale-in transition: reducing a Redis Cluster from four primary master nodes down to three. 

The metric for success is strict data integrity: measuring the volume of keys lost and the number of hash slots permanently orphaned. By performing this transition under quiescent conditions, the experiment yields a binary, reproducible proof of how each mechanism handles state.

\subsection{Phase 1: Environment Scorch and Initialisation}
To prevent state contamination, every iteration begins by systematically destroying the \texttt{redis} namespace, uninstalling any active Helm charts, deleting all Persistent Volume Claims (PVCs), and purging residual \texttt{ServiceMonitor} resources. The namespace is then recreated, ensuring an identical blank slate for both the native HPA and the operator pathways.

\subsection{Phase 2: Deployment of the Baseline Topology}
A four-master Redis Cluster is deployed without any replica nodes. Running without replicas is a deliberate experimental control: it prevents native high-availability failover from temporarily masking the architectural failure of a pod deletion.

\begin{itemize}
    \item \textbf{Native HPA Scenario:} A \texttt{StatefulSet} is deployed with \texttt{replicas: 4}. Because a \texttt{StatefulSet} cannot form a Redis topology natively, a \texttt{redis-cli -{}-cluster create} command is executed sequentially against the four pod IPs to allocate the \num{16384} hash slots (\cite{k8s:statefulset}).
    \item \textbf{Operator Scenario:} A \texttt{RedisCluster} Custom Resource is applied with \texttt{clusterSize: 4}. The operator autonomously coordinates the \texttt{CLUSTER MEET} commands and slot allocations.
\end{itemize}
In both scenarios, the script halts until the cluster reports a \texttt{cluster\_state:ok} and confirms all \num{16384} slots are covered.

\subsection{Phase 3: Deterministic Data Population}
Once the four-node baseline is healthy, exactly \num{5000} simple string keys (formatted as \texttt{key:\$i}) are written to the cluster via \texttt{redis-cli}. Because no hash tags are used, the Redis routing algorithm distributes the \num{5000} keys uniformly across the \num{16384} slots, resulting in approximately \num{1250} keys residing on each of the four master nodes. A baseline snapshot is recorded to verify the presence of the dataset.

\subsection{Phase 4: The Scale-In Event}
With the cluster settled and fully populated, the scale-in command is issued. 

\begin{itemize}
    \item \textbf{Native HPA Scenario:} The script executes \texttt{kubectl scale statefulset -{}-replicas=3}. This perfectly mimics the action taken by a reactive HPA controller. The Kubernetes scheduler immediately issues a termination signal to the highest-ordinal pod (\texttt{redis-3}).
    \item \textbf{Operator Scenario:} The script executes \texttt{kubectl patch rediscluster -{}-type merge -p '\{"spec":\{"clusterSize":3\}\}'}. This mimics the action of an event-driven scaling trigger. The operator intercepts the size reduction, initiates a live migration to drain the targeted master's slots onto the surviving nodes, and only permits pod termination once the node is empty.
\end{itemize}

\subsection{Phase 5: Evaluation and Probing}
After the designated pod is terminated, a final state snapshot is taken. The total surviving keys and the total covered hash slots are recorded. To definitively test cluster availability, the script executes five targeted read probes. Because the Redis Cluster specification requires full \num{16384} slot coverage by default, any permanent loss of slots will cause the cluster to reject the read probes with a \texttt{CLUSTERDOWN} error (\cite{redis:clusterspec}). The comparison of the before and after states forms the empirical verdict presented in Chapter~\ref{sec:results}.
