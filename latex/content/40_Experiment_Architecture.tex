\section{Experiment Architecture}
\label{sec:architecture}

This section describes the architecture of the experimental testbed once it has been
reduced to the minimum required in order to observe a planned scale-in in isolation.
Because the study deliberately excludes live load, an application entrypoint, and any
autoscaler controller (Section~\ref{sec:test-flow}), the architecture is correspondingly
lean: every component resides inside a single Kubernetes cluster, and the experiment is
driven not by external traffic but by a control script that writes a known dataset, removes
exactly one master, and reads back the result. The two mechanisms under
investigation---the native StatefulSet contraction that reproduces the Horizontal Pod
Autoscaler's scale-down action, and the Opstree Redis Operator's topology-aware
drain---are realised as two mutually exclusive, interchangeable data-tier modules within an
otherwise identical environment, so that any measured difference can be attributed solely
to the scaling mechanism. The procedure that exercises this architecture is presented
separately in Section~\ref{sec:test-flow}, and the conceptual description of each individual
technology is given in Section~\ref{sec:technologies}.

% ============================================================
\subsection{Physical Substrate: the K3s Cluster}
\label{subsec:cluster-substrate}
% ============================================================

The cluster is a k3s distribution running on six mini-PCs (four-core CPU, 8\,GB
RAM each), one acting as a combined control-plane and worker node and the remaining five as
workers (\cite{k3s:docs}). k3s is chosen for its small footprint on resource-constrained
hardware while remaining fully API-conformant. The in-cluster components are organised into
three Kubernetes namespaces, which also structure the subsections below: \texttt{redis} (the
stateful data tier together with both scaling configurations), \texttt{ot-operators} (the
Opstree Redis Operator that the operator scenario depends upon), and \texttt{monitoring}
(the observability stack on which the results are captured). Because the experiment operates
on four masters before contracting to three, the leader anti-affinity described below is able
to place each master on a distinct physical node.

% ------------------------------------------------------------
\subsection{The Experiment Driver}
\label{subsec:driver}
% ------------------------------------------------------------

In place of the external load generator and application entrypoint of a conventional
benchmarking harness, the sole driver of this testbed is a single control script,
\texttt{data-safety-experiment.sh}, executed on the control-plane node with its
\texttt{KUBECONFIG} pointed at the local k3s configuration. The script orchestrates the
entire run through \texttt{k3s kubectl}, \texttt{helm}, and \texttt{redis-cli} invoked via
\texttt{kubectl exec} into the surviving ordinal-$0$ leader pod. Crucially, there is no
FastAPI entrypoint, no \texttt{k6} load generator, and neither an HPA nor a KEDA controller
acting on the cluster; the script instead reproduces by hand the precise scale-down action
that each autoscaler would otherwise perform. Because that script is the only process that
ever writes to Redis, the data tier is quiescent throughout, and the measured outcome is
therefore a deterministic property of the scaling mechanism rather than of any incidental
traffic.

% ------------------------------------------------------------
\subsection{The \texttt{redis} Namespace: Stateful Data Tier and Scaling Configurations}
\label{subsubsec:ns-redis}
% ------------------------------------------------------------

The \texttt{redis} namespace contains the stateful data tier and the manifests for both
scaling scenarios. Only one scenario is ever active at a time; the setup script scorches the
namespace between runs. A Redis Cluster partitions its key space into $16{,}384$ hash slots
distributed across master nodes (\cite{redis:clusterspec}), and the two scenarios differ
precisely in \emph{who} manages those slots when the master count changes.

\paragraph{HPA scenario (self-managed cluster).}
Here the cluster is assembled from native Kubernetes primitives. A \texttt{ConfigMap}
supplies a minimal \texttt{redis.conf} with \texttt{cluster-enabled yes}; a headless
\texttt{Service} (\texttt{clusterIP: None}) gives each pod a stable DNS identity; and a
\texttt{StatefulSet} runs Redis with an \texttt{oliver006} exporter sidecar on port
\texttt{9121} (Listing~\ref{lst:redis-statefulset}). Although the manifest declares six
replicas, the data-safety experiment scales the StatefulSet to \texttt{START\_MASTERS} pods
and forms a \emph{masters-only} cluster imperatively with
\texttt{redis-cli -{}-cluster create} (deliberately omitting \texttt{-{}-cluster-replicas}, so
that the cliff is exposed without a replica to mask it); the topology that a
\texttt{StatefulSet} manifest cannot itself express is therefore assigned at runtime
(\cite{k8s:statefulset,redis:clusterspec}). The per-pod CPU requests that the manifest
annotates as serving an HPA's utilisation calculation (\cite{k8s:hpa}) are simply unused in
this isolated run, since no autoscaler is deployed; the scale-in is instead driven by hand.
A \texttt{ServiceMonitor} (Listing~\ref{lst:servicemonitor-hpa}) wires the exporter into
Prometheus.

\begin{lstlisting}[caption={Redis \texttt{ConfigMap}, headless \texttt{Service}, and \texttt{StatefulSet} (\texttt{redis-hpa-cluster.\ac{yaml}}).},label={lst:redis-statefulset}]
apiVersion: v1
kind: ConfigMap
metadata: { name: redis-min-config, namespace: redis }
data:
  redis.conf: |
    cluster-enabled yes
    cluster-config-file nodes.conf
    cluster-node-timeout 5000
    appendonly no
---
apiVersion: v1
kind: Service
metadata:
  name: redis-headless
  namespace: redis
  labels: { app: redis }
spec:
  clusterIP: None                 # headless: per-pod DNS for slot-aware routing
  ports:
    - { port: 6379,  name: redis }
    - { port: 16379, name: gossip }
    - { port: 9121,  name: metrics }
  selector: { app: redis }
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: redis, namespace: redis }
spec:
  serviceName: redis-headless
  replicas: 6                      # experiment scales this to START_MASTERS and forms masters-only
  selector:
    matchLabels: { app: redis }
  template:
    metadata:
      labels: { app: redis }
    spec:
      containers:
        - name: redis
          image: redis:7.2-alpine
          command: ["redis-server", "/etc/redis/redis.conf"]
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
          volumeMounts:
            - { name: conf, mountPath: /etc/redis }
        - name: redis-exporter
          image: ghcr.io/oliver006/redis_exporter:latest
          ports:
            - { containerPort: 9121, name: metrics }
          env:
            - { name: REDIS_ADDR, value: "redis://localhost:6379" }
          resources:
            requests: { cpu: "50m", memory: "64Mi" }
      volumes:
        - name: conf
          configMap: { name: redis-min-config }
\end{lstlisting}

\begin{lstlisting}[caption={\texttt{ServiceMonitor} for the HPA scenario exporter (\texttt{redis-servicemonitor.yaml}).},label={lst:servicemonitor-hpa}]
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: redis-monitor
  namespace: redis
  labels: { release: prometheus }  # adopted by kube-prometheus-stack
spec:
  selector:
    matchLabels: { app: redis }
  endpoints:
    - { port: metrics, interval: 15s }
\end{lstlisting}

\paragraph{Operator scenario (operator-managed cluster).}
Here the data tier is declared rather than assembled. The Opstree Redis Operator is given a
desired \texttt{clusterSize} through its \texttt{RedisCluster} custom resource, and the
operator creates the leader and follower \texttt{StatefulSet}s, forms the cluster, and---most
importantly for this study---reshards slots when the size changes
(\cite{k8s:operator,opstree:redisoperator}). The resource is deployed via the operator's Helm
chart, configured by the values file in Listing~\ref{lst:operator-values}: the baseline
\texttt{clusterSize} of $3$ is overridden to \texttt{START\_MASTERS} at deploy time with a
\texttt{-{}-set} flag, the leader and follower replica counts are left unset so that
\texttt{clusterSize} alone drives the master count, leader anti-affinity spreads masters
across nodes, and the same \texttt{oliver006} exporter is enabled for metric parity with the
HPA scenario. In this isolated experiment the size is changed directly, by patching the
custom resource, rather than by an event-driven KEDA trigger. As in the HPA scenario, a
standalone \texttt{ServiceMonitor} (Listing~\ref{lst:servicemonitor-operator}) is required,
because neither the operator nor the chart flag creates one.

\begin{lstlisting}[caption={Opstree Helm values producing the \texttt{RedisCluster} (\texttt{redis-operator-cluster-values.yaml}).},label={lst:operator-values}]
redisCluster:
  clusterSize: 3                   # overridden to START_MASTERS via --set at deploy time
  persistenceEnabled: false        # ephemeral, matching the HPA scenario
  resources:
    requests: { cpu: "100m", memory: "128Mi" }
    limits:   { cpu: "250m", memory: "256Mi" }
  leader:
    replicas: null                 # null => clusterSize drives the master count
    affinity:
      podAntiAffinity:             # prefer one master per node
        preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels: { app: redis-cluster-leader }
            topologyKey: kubernetes.io/hostname
  follower:
    replicas: null
redisExporter:
  enabled: true
  image: ghcr.io/oliver006/redis_exporter
  tag: latest
  resources:
    requests: { cpu: "50m", memory: "64Mi" }
serviceMonitor:                    # chart flag is a no-op here; see standalone SM below
  enabled: true
  interval: 15s
  extraLabels: { release: prometheus }
\end{lstlisting}

\begin{lstlisting}[caption={Standalone \texttt{ServiceMonitor} for the operator's exporters (\texttt{redis-servicemonitor.yaml}).},label={lst:servicemonitor-operator}]
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: redis-operator-monitor
  namespace: redis
  labels: { release: prometheus }
spec:
  selector:                        # selects both leader-metrics and follower-metrics services
    matchLabels:
      app.kubernetes.io/component: metrics
      redis_setup_type: cluster
  endpoints:
    - { port: redis-exporter, interval: 15s }
\end{lstlisting}

\subsection{The \texttt{ot-operators} Namespace: the Redis Operator}
\label{subsubsec:ns-operator}
% ------------------------------------------------------------

The operator scenario depends on a single cluster-wide controller that is installed once, via
Helm, and shared across runs; it is not redeployed by the per-experiment script. The
\texttt{ot-operators} namespace runs the Opstree Redis Operator, a custom controller that
watches \texttt{RedisCluster} resources and reconciles them into running clusters, encoding
the Redis-specific domain knowledge---cluster formation, slot assignment, and topology-aware
resharding---that Kubernetes' generic primitives lack (\cite{k8s:operator}). It is precisely
this controller that performs the graceful drain measured in the operator scenario, migrating
a departing master's slots to the survivors before the pod is removed. Notably, KEDA plays no
part in this isolated experiment: because the scale-in is triggered by directly patching the
\texttt{clusterSize} field rather than by an application-level metric, no event-driven
autoscaling layer is installed. The HPA scenario, in turn, uses no controller of any kind;
its scale-in is the bare StatefulSet contraction that the control script issues by hand.

% ------------------------------------------------------------
\subsection{The \texttt{monitoring} Namespace: Observability and Capture}
\label{subsubsec:ns-monitoring}
% ------------------------------------------------------------

The \texttt{monitoring} namespace hosts the observability stack, deployed once from the
\texttt{kube-prometheus-stack} Helm chart, which bundles Prometheus and Grafana
(\cite{artifacthub:kube-prometheus-stack}). It is identical across both experimental
conditions. The values overrides are shown in Listing~\ref{lst:prometheus-values}:
control-plane scrape jobs that do not apply to a k3s distribution are disabled, and both
Prometheus and Grafana are exposed via \texttt{NodePort}. Prometheus discovers its scrape
targets through the \texttt{ServiceMonitor} resources defined in the \texttt{redis} namespace
(Listings~\ref{lst:servicemonitor-hpa} and~\ref{lst:servicemonitor-operator}), which point it
at the Redis exporters (\cite{prometheus:overview}). Those exporters expose the slot- and
key-level series---most importantly \texttt{redis\_cluster\_slots\_assigned} and
\texttt{redis\_db\_keys}---on which Grafana (\cite{grafana:github}) renders the before-and-after
panels that document each scale-in. The \texttt{enableRemoteWriteReceiver} flag, originally
provisioned so that an off-cluster generator could push client-side metrics, is inert in this
isolated configuration but has been left in place as a harmless default.

\begin{lstlisting}[caption={\texttt{kube-prometheus-stack} Helm values (\texttt{my-prometheus-values.yaml}).},label={lst:prometheus-values}]
kubeControllerManager: { enabled: false }   # not exposed by k3s
kubeEtcd:              { enabled: false }
kubeProxy:            { enabled: false }
kubeScheduler:        { enabled: false }
grafana:
  service: { type: NodePort }
prometheus:
  service: { type: NodePort }
  prometheusSpec:
    enableRemoteWriteReceiver: true          # inert here; retained as a harmless default
\end{lstlisting}

\subsection{End-to-End Measurement Flow}
\label{subsec:data-flow}
% ============================================================

Bringing the layers together, a single experimental run traverses the following path, which
replaces the request-driven path of a load-tested system with a measurement-driven one:

\begin{enumerate}
    \item The control script populates a known, exact dataset by executing
    \texttt{redis-cli} inside the ordinal-$0$ leader pod, writing every key directly; as the
    only writer, it leaves the cluster quiescent.
    \item The script records the \emph{before} snapshot, reading \texttt{cluster\_state} and
    \texttt{cluster\_slots\_ok} from \texttt{redis-cli cluster info} and the key total from
    \texttt{redis-cli -{}-cluster check}.
    \item The script triggers the one-master scale-in, either by contracting the StatefulSet
    (HPA scenario) or by patching \texttt{clusterSize} on the custom resource (operator
    scenario), thereby invoking the operator's reshard.
    \item The script records the \emph{after} snapshot and issues a direct read probe, whose
    response under the default \texttt{cluster-require-full-coverage} policy is effectively
    binary.
    \item Throughout, the exporter sidecars expose the cluster metrics, which Prometheus
    scrapes on its interval; Grafana queries Prometheus and renders the slot- and key-level
    series, providing the panels recorded in Section~\ref{sec:results}.
\end{enumerate}

Every component on this path other than the data-tier module in step~3 is held constant
across the two experimental conditions, so that the comparison in Section~\ref{sec:results}
isolates the scaling mechanism.
